# 框架设计：以高质量信息供给为目标的抽象

> 状态：v1.0 最小闭环已实现并通过基线测试（见文末）。
> 本文回答一个核心问题：**Agent 框架要如何设计，才能给 LLM 尽可能高质量的信息？**

## 1. 核心心智模型

**LLM 是一个每次醒来都失忆的专家**——它没有记忆、没有目标、没有"上一帧"的概念，每次调用都是一张白纸看一张图。

由此推出框架与 LLM 的责任分界：

```
框架的责任（工程问题，可控）：  信息无损地进 → 指令无损地出 → 忠实执行
LLM 的责任（智能问题，不可控）：看到信息后做什么决策
```

框架是管道，管道的天职是**不增加额外的失真**。"LLM 笨不笨"不归框架管——框架的价值在于：把"LLM 能不能"变成 benchmark 上可测量的数字，而不是发布前要解决的问题。

**"高质量信息"的工程定义**：让一个每次都失忆的决策者，在零上下文下也能做出合理决策。

## 2. 四条供给通道（信息包）

LLM 每步需要四样东西，缺一不可：

| 供给 | 作用 | 低质量反例 |
|---|---|---|
| **当前观测**（截图 + 结构化预分析） | 它"看"的世界 | 只发原始截图，小字 UI 全靠多模态模型瞎猜 |
| **任务目标**（每步常驻） | 它"为何而战" | 第 50 步不提醒目标，LLM 原地打转 |
| **行动历史摘要**（分层压缩） | 它"刚干了什么" | 50 步完整对话塞进 prompt，token 爆炸且注意力稀释 |
| **可用动作词汇表**（输出契约） | 它"能说什么话" | 只说"你可以操作键鼠"，LLM 输出自然语言操作描述，解析天天失败 |

**高质量 ≠ 信息越多**。注意力稀释会让关键信息淹没在噪声里；表示形式比信息量更重要（"敌人血量剩1/3"用结构化字段 `enemy_hp: 0.33` 供给，比让 LLM 自己看截图省下视觉推理预算）。Agent 的手艺是**选择性供给**：什么常驻、什么进滑动窗口、什么压成一行摘要、什么果断丢弃。

## 3. 组件架构

```
┌─────────────────── AgentRunner（循环编排）───────────────────┐
│                                                              │
│  Environment ──→ Perception ──→ ContextAssembler ──→ LLM     │
│  (capture/act)   (看懂一帧)     (组装信息包)      │          │
│       ▲                            ▲             ▼          │
│       │                     HistoryManager    ActionParser   │
│       └────────────────────────────────────────┘ (校验/执行) │
└──────────────────────────────────────────────────────────────┘
```

### 3.1 Environment（游戏侧契约）

框架核心只认三个方法，任何游戏接入只需实现这三个：

```python
class Environment(ABC):
    def capture(self) -> FrameAnalysis: ...
    """给 LLM 看世界：返回当前画面（截图 + 可选感知预分析）"""

    def act(self, action: Action) -> None: ...
    """让 LLM 动手：执行键鼠原语"""

    def check(self, task: Task) -> Status: ...
    """给裁判哨子：核实任务成败 SUCCESS / FAIL / RUNNING"""
```

**关键决策 1——Action 画在键鼠原语层**：`key / click / move / wait` 是所有游戏的最大公约数，进核心接口；高层动作（"攻击""合成"）是游戏私有的，留给适配器扩展。画得越低越通用、Agent 越难；这是刻意选择——难度真实，且永不过时。

**关键决策 2——check() 的标准与机制分离**：

```
成败的标准（WHAT）── 因任务而异，使用者声明，随 Task 传入
成败的机制（HOW）── 所有游戏通用，框架/环境提供
```

框架不替用户定标准，只定**标准的表达方式（Task 声明式条件）和执行方式（check 机制）**。类比高考：考题各省不同，但密封阅卷、机读流程全国统一。

**关键决策 3——最小核心 + 可选增强**：`save/restore` 等增强方法进可选层（benchmark 复位刚需，但不是每个游戏都支持存档）。判断标准只有一条：**没有它，Agent 循环转不转？** 转得起来就不进核心。

**关键决策 4——契约与通用实现分层**：对桌面窗口游戏，`capture`（截屏+OCR 感知）与 `act`（键鼠注入）跨游戏完全通用，差异只在构造参数（截哪块区域、是否 OCR、执行节奏）。因此框架内置 `WindowEnv` 通用实现类（含图像坐标→屏幕坐标的自动平移），桌面游戏适配者**只需继承并实现 check/reset**。`Environment` 契约本身保持最小，为仿真器（EmulatorEnv）、浏览器（BrowserEnv）等 capture/act 结构不同的源留接入位。

### 3.2 Perception（感知器）

把一帧画面变成结构化情报 `FrameAnalysis`：截图原图 + 可交互元素列表（文字、坐标、置信度）。

**关键决策 4——一帧双通道表示**：原图给多模态 LLM 看，结构化文本给文本推理用，两者同时供给。纯像素通道：信息全但当前多模态模型读屏易漏小字；纯结构化通道：LLM 好消化但被预过滤。混合通道让 LLM 自己取用，两种表示的差异本身是研究点。

坐标数据是一等公民：**OCR 检测出的元素坐标就是 LLM 可点击的目标**。感知失败（如 OCR 异常）降级为纯图像通道，不打断循环。

### 3.3 ContextAssembler（上下文组装器）——框架的灵魂

不采集任何数据，只做**选择与排版**。三条排版纪律即"高质量"的工程定义：

1. **目标常驻**：任务目标每步重复，防第 50 步失忆打转
2. **历史分层**：最近 N 步保留动作和结果，更早的压成一行摘要
3. **噪声剪枝**：上一步没变化的信息不重复发；解析错误显式回喂（"你的输出不合法，错误是…请修正"）

### 3.4 HistoryManager（历史管理器）

记录每步 `(分析摘要, 动作, 结果)`，对外只暴露 `recent(n)` 和 `summary()` 视图。与 LLM 完全解耦——将来换记忆策略（向量检索、跨窗口笔记），只动这一个类。

### 3.5 ActionParser（动作解析器）——LLM 输出的安检门

用结构化输出（JSON schema）约束 LLM 只能说词汇表里的话：解析、校验类型、校验参数、坐标越界裁剪。**解析失败不崩循环**——错误信息作为反馈回喂重试。没有这层，一次格式抽风就崩掉整个循环；它看似工程细节，实际决定了 LLM 发挥的下限。

### 3.6 AgentRunner（循环编排）与 LLM 适配器

```python
# 完整闭环，即框架的全部流程
while True:
    obs = env.capture()                       # 眼：采集
    prompt = assembler.build(task, obs, history.view())   # 信息包组装
    action = parse(decider(prompt, obs.screenshot))       # 大脑 + 安检门
    env.act(action)                           # 手：执行
    if env.check(task) is not RUNNING: break  # 哨：判分
```

LLM 可插拔的关键是一个极窄的 Decider 接口：`async decide(prompt, screenshot) -> str`。本地 Ollama 与云端模型共用同一接口，benchmark 表格上两行数字见高下。

## 4. 责任边界验收测试

设计对不对，用这个问题自检：**换一个游戏 / 换一个 LLM / 换一种记忆策略，分别要改几个组件？**

正确答案：换游戏→只写新 Environment 适配器；换 LLM→只动配置；换记忆→只动 HistoryManager。**任何一项改动波及两个以上组件，就说明边界切错了。**

框架的天花板 ≠ LLM 的天花板：LLM 换代升级，框架自动受益——因为它只做"供给"，不做"智能"。基础设施的生命周期远长于任何一代模型。

## 5. 研究扩展点（Research Extension Points）

> 定位口号：**我们把管道冻住，好让你的想法成为唯一的变量。**

框架同时服务"用 Agent 的人"和"研究 Agent 的人"，切分方式不是"用户 vs 研究者"，而是**该冻结什么、该开放什么**：

| 层 | 策略 | 理由 |
|---|---|---|
| 管道（循环骨架、动作解析、重试机制） | **冻结** | 这是实验的控制变量。harness 不统一则分数不可比——ARC-AGI-3 同一模型标准 harness 62.7% vs 定制 harness 99.9% 的争议即为例证。冻结管道保证：替换某个机制后的提升只能归因于该机制，而非工程质量差异 |
| 机制（决策/记忆/感知/组装） | **开放为插槽** | 这是研究者的实验变量 |
| 环境 + 考题 | **共享** | 这是考场。Gym 之于 RL、SWE-bench 之于软件工程 Agent——环境标准化恰恰释放研究，没人需要自建 Pong |

### 可换插槽清单

| 研究变量 | 替换点 | 形态 |
|---|---|---|
| 决策/提示策略 | `Decider` | 一个 async 函数（收 prompt+截图，吐动作文本） |
| 记忆机制 | `HistoryManager` | 一个类 |
| 上下文组装策略 | `ContextAssembler` | 一个类 |
| 感知/grounding | `Perception` | 一个类 |
| 模型对比 | `make_llm_decider` | 一行配置 |

替换任一插槽的验收标准即第 4 节的责任边界测试：只动一个组件，框架其余部分零改动。

### 诚实边界

- **循环骨架本身**不在研究支持面内（分层控制、多智能体、树搜索式循环需 fork）——历史上这类研究者本就自建 harness，框架不为他们设计
- **无训练接口**：刻意不设 reward 信号（LLM 推理驱动，非 RL 训练框架），训练场景不适用
- 目标研究受众是**没有资源自建环境+考题+benchmark 的研究者**（研究生、独立研究者、小实验室），而非已有全套基建的顶级实验室

### 世界模型对接舱

`Environment` 抽象同时是世界模型研究的接口：一个学习出来的世界模型（生成式模拟器）可以**作为一个 Environment 直接插入**——用模型环境替代真实游戏跑 benchmark，即 Real2Sim 的实验形态。"用户口"与"研究者口"在此是同一个口。

**基线数据**（qwen2.5vl:7b，MockEnv 点方块任务，n=10，2026-09-19）：

```
命中率 70.0%（7/10，全部为第 1 步命中）
解析错误率 0/10
平均耗时 9.1s/次
```

**反馈注入实验**（2026-09-27，同种子同考题，对照 70% 基线）：任务未完成时，prompt 显式注入"上一步动作 + 不要原样重复 + 修正坐标"反馈，MockEnv 同时在 notes 中解释红点为历史落点。结果：**命中率 70% → 80%**；基线中僵死循环的 run 3 第二步即修正命中（click(320,400) → click(300,350)，靶位 291,351），机制假设验证成立。但 run 6/7 的僵死循环未被打破——7B 模型在部分困难场景完全无视文本反馈。后续方向：反馈前置/逐级升格、runner 层重复动作机械拦截、下半屏 Y 坐标系统性偏差调查（三次失败靶位 y 均 >350）。
